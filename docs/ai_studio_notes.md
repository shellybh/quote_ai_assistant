# ניסויים ב-Google AI Studio — שלב 0

**מטרה:** לבדוק לפני שכותבים קוד שהמודל מצליח בשלוש המשימות. לכל משימה צריך פרומפט אחד שעבד (בדיקת הסיום של שלב 0).
**מה מדביקים:** רק סעיפים מהמחירון הפומבי וטקסט בדיוני. אסור להדביק הצעות אמיתיות, לקוחות או את שם העסק,
כי בשכבה החינמית Google רשאית להשתמש בתוכן לשיפור המוצרים שלה.

## הגדרות לכל הניסויים
1. נכנסים ל-<https://aistudio.google.com>, עם אותו חשבון של מפתח ה-API.
2. **קודם בודקים את המכסות:** בתפריט נכנסים לדף Rate limit של הפרויקט, ורושמים בטבלה בסוף המסמך כמה בקשות מותר
   לדקה וליום (RPM, RPD) לכל אחד מהמודלים: `gemini-3.8-flash`, `gemini-3.6-flash`, `gemini-3.5-flash-lite`, `gemini-embedding-2`.
   Google לא מפרסמת את המספרים האלה בתיעוד, ולכן אפשר לראות אותם רק שם.
3. Create prompt (צ'אט חדש). בצד ימין מגדירים:
   - **Model:** מתחילים ב-`gemini-3.5-flash-lite` (500 פניות ביום). אם נשארת מכסה, מריצים את אותו ניסוי ב-`gemini-3.8-flash` (20 פניות ביום) ומשווים.
   - **Temperature:** 0. (בפועל ההגדרה לא מופיעה למודל הזה. בשלב 1 התברר ש-Google לא מאפשרת לשנות אותה בו, ולכן היא לא נשלחת. ראו סעיף 5.2 באפיון.)
   - **Structured output:** מפעילים ומדביקים את סכמת ה-JSON של המשימה (כפתור Edit).
   - **Thinking:** הכי נמוך שאפשר. אם יש טעויות, מעלים ובודקים אם זה עוזר.
4. את ההוראות מדביקים ב-**System instructions**, ואת הקלט בהודעה.
5. אחרי כל ריצה רושמים בטבלת התוצאות: מה עבד, מה לא, וכמה זמן לקח. אם הפרומפט משתנה, שומרים את הגרסה שעבדה.

## ניסוי 1 — פירוק תיאור עבודה (Intake)

**System instructions:**
```
אתה עוזר לעסק לשימור מבנים. תקבל תיאור עבודה בעברית חופשית, כפי שבעל העסק מקליד אחרי ביקור באתר.
פרק אותו לרשימת עבודות נפרדות. לכל עבודה:
- task: תיאור קצר וברור של העבודה, במונחים מקצועיים של שימור ובנייה.
- quantity: הכמות אם נאמרה במפורש, אחרת null. אל תנחש כמות.
- unit: היחידה אם נאמרה (מ"ר, מ', יח', מ"ק), אחרת null.
- location: היכן במבנה (חזית, גג, מרפסת...) אם נאמר, אחרת null.
אל תוסיף עבודות שלא נאמרו. אל תציין מחירים. החזר JSON בלבד לפי הסכמה.
```

**סכמה:**
```json
{
  "type": "object",
  "properties": {
    "tasks": {
      "type": "array",
      "items": {
        "type": "object",
        "properties": {
          "task": {"type": "string"},
          "quantity": {"type": "number", "nullable": true},
          "unit": {"type": "string", "nullable": true},
          "location": {"type": "string", "nullable": true}
        },
        "required": ["task", "quantity", "unit", "location"]
      }
    }
  },
  "required": ["tasks"]
}
```

**קלטים לבדיקה** (בדיוניים):
1. `בחזית הצפונית הטיח מתקלף בערך 120 מטר, צריך לחדש ולצבוע בסיד. יש גם צמחייה על הקיר ושני מזגנים להזיז.`
2. `מעל החלונות בקומה השנייה הקרניז שבור, 3 מדרגות, משהו כמו 14 מטר אורך. וגם אף המים מתחתיו.`
3. `לשקם 6 חלונות עץ ישנים, כל אחד בערך מטר על מטר, ולצבוע אותם. 2 תריסים ערביים צריכים רפפות חדשות.`
4. `רטיבות בקירות למטה בכניסה, הטיח נופל עד גובה מטר. אורך הקיר כ-18 מ'.`
5. `גג שטוח 85 מ"ר דולף, להוריד את האיטום הישן ולעשות חדש בשתי שכבות. המרזבים סתומים.`

**מה בודקים:** כל עבודה מופיעה פעם אחת. כמות מופיעה רק כשנאמרה (בקלט 2 "14 מטר" כן, וגם ב-4 "18 מ'" כן). אין עבודות מומצאות.

**System instructions — גרסה 2** (אחרי ריצת v1: פרטים שמבחינים בין סעיפים נעלמו, ושתי עבודות אוחדו לאחת):
```
אתה עוזר לעסק לשימור מבנים. תקבל תיאור עבודה בעברית חופשית, כפי שבעל העסק מקליד אחרי ביקור באתר.
פרק אותו לרשימת עבודות נפרדות. כל פעולה שהייתה מופיעה כשורה נפרדת במחירון היא עבודה נפרדת (למשל טיפול ברטיבות וחידוש טיח הן שתי עבודות).
לכל עבודה:
- task: תיאור קצר וברור של העבודה, במונחים מקצועיים של שימור ובנייה. שמור בתיאור כל פרט שעשוי להבדיל בין סעיפי מחירון: מספר מדרגות, מידות או גודל של פריט, גובה, חומר, מספר שכבות וסוג גמר.

- unit: היחידה אם נאמרה (מ"ר, מ', יח', מ"ק), אחרת null.
- location: היכן במבנה (חזית, גג, מרפסת...) אם נאמר, אחרת null.
אל תוסיף עבודות שלא נאמרו. אל תציין מחירים. החזר JSON בלבד לפי הסכמה.
```

## ניסוי 3 — ניסוח ממצא בבדיקת הצעה (Reviewer)

הבדיקה עצמה רצה בקוד. המודל רק מנסח את הממצא, ו**אינו מקבל מחירים**: הוא מקבל יחס בלבד ("פי 2.1").

**System instructions:**
```
אתה עוזר לעסק לשימור מבנים. בדיקה אוטומטית מצאה בעיות בהצעת מחיר לפני שליחה.
לכל ממצא כתוב, בעברית פשוטה ומקצועית, משפט אחד עד שניים בכל שדה:
- problem: מה הבעיה.
- why: למה זה חשוב (סיכון כספי, משפטי או אי-הבנה עם הלקוח).
- suggestion: מה כדאי לעשות.
אל תמציא ממצאים נוספים, אל תציין סכומים ואל תשנה את line_code. החזר JSON בלבד.
```

**סכמה:**
```json
{
  "type": "object",
  "properties": {
    "findings": {
      "type": "array",
      "items": {
        "type": "object",
        "properties": {
          "line_code": {"type": "string", "nullable": true},
          "kind": {"type": "string"},
          "problem": {"type": "string"},
          "why": {"type": "string"},
          "suggestion": {"type": "string"}
        },
        "required": ["line_code", "kind", "problem", "why", "suggestion"]
      }
    }
  },
  "required": ["findings"]
}
```

**קלט לדוגמה** (מדביקים כ-JSON):
```json
[
  {"line_code": null, "kind": "missing_condition", "details": "ההצעה כוללת עבודות בחזית (טיח, קרניז) ואין בה תנאי פיגום: לא 'כלול' ולא 'לא כלול'."},
  {"line_code": "01.09.001.0270", "kind": "unusual_price", "details": "מחיר היחידה גבוה פי 2.1 מהחציון של אותו סעיף ב-12 הצעות קודמות."},
  {"line_code": "01.09.001.0230", "kind": "wrong_unit", "details": "הסעיף נמדד במחירון במטר אורך (מ'), ובהצעה היחידה היא מ\"ר."},
  {"line_code": "01.09.001.0100", "kind": "wording", "details": "בתיאור השורה שונה ל'חידוש טיח לפי הצורך' — לא ברור מה כלול ובאיזה היקף."}
]
```

**System instructions — גרסה 2** (אחרי ריצת v1: הפרטים מה-details נעלמו, ונוספו הנחות שלא נאמרו):
```
אתה עוזר לעסק לשימור מבנים. בדיקה אוטומטית מצאה בעיות בהצעת מחיר לפני שליחה.
לכל ממצא כתוב, בעברית פשוטה ומקצועית, משפט אחד עד שניים בכל שדה:
- problem: מה הבעיה. שמור את הפרטים מתוך details: יחס (למשל "פי 2.1"), מספר ההצעות שנבדקו, היחידות (מ' או מ"ר) וציטוט של הנוסח. בעל העסק צריך להבין מה בדיוק לתקן בלי לחפש.
- why: למה זה חשוב (סיכון כספי, משפטי או אי-הבנה עם הלקוח).
- suggestion: מה כדאי לעשות. במחיר חריג: לבדוק אם זו טעות הקלדה, ואם המחיר מכוון, להשאיר אותו או להסביר אותו בהצעה. אל תמליץ להוריד או להעלות מחיר.
השתמש רק במידע שבממצא. אל תניח פרטים שלא נאמרו (למשל מכרז, מחירי שוק או נוסחה).
אל תמציא ממצאים נוספים ואל תשנה את line_code. מותר לציין יחס ויחידות מידה, אבל אסור לציין סכום כסף או מחיר. החזר JSON בלבד.
```

**מה בודקים:** ארבעה ממצאים בדיוק, בלי ממצאים נוספים, בלי סכומים, ואותו `line_code`. כל שדה בן משפט עד שניים, בשפה שבעל עסק מבין.
